1. 矩阵-向量乘（GEMV）在大模型推理中的地位与算术强度瓶颈

通用矩阵-向量乘（General Matrix-Vector Multiplication, GEMV: \(y = A x + \text{bias}\)）是线性代数与深度学习中的基础算子。 尤其在大语言模型（LLM）的自回归解码生成阶段（Decode Phase）中，每生成一个新 Token，KV Cache 投影以及 MLP 投影都是以单个 Token（即批次维度 \(\text{Batch}=1\)）输入线性层。此时通用的矩阵乘（GEMM: \([M, K] \times [K, N]\)）必然退化为矩阵-向量乘（GEMV: \([M, N] \times [N, 1] \to [M, 1]\)）： - 极低的算术强度（Memory-Bound 典型代表）： 设矩阵 \(A \in \mathbb{R}^{M \times N}\)，向量 \(x \in \mathbb{R}^N\)。 - 理论计算量：每个元素需要 1 次乘法和 1 次加法，总浮点运算量为 \(2 M N\text{ FLOPs}\)； - 显存访存量：必须从全局内存中加载整个权重矩阵 \(A\)（\(4MN\) 字节），读取向量 \(x\)（\(4N\) 字节），并写回结果 \(y\)（\(4M\) 字节）。 - 其算术强度上限仅为： \[I = \frac{2 M N}{4 M N + 4 N + 4 M} \approx \frac{2 M N}{4 M N} = 0.5 \text{ FLOPs/Byte}\] 在标称带宽 \(3.35\text{ TB/s}\) 的 H100 GPU 上，GEMV 的理论算力上限只有 \(\approx 1.67\text{ TFLOPS}\)（远低于硬件 \(1000\text{ TFLOPS}\) 峰值）。 因此，GEMV 的优化哲学在于：极致榨干全局显存读取带宽，确保权重矩阵 \(A\) 的合并访存，并最大化向量 \(x\) 在 L1/L2 缓存中的数据复用。

2. 行级并行与 Block 映射架构（如图 3-1 与图 3-2 所示）

在行优先（Row-Major）存储格式下，矩阵 \(A\) 的同一行元素在物理内存地址中是严格连续排列的。

A. 为什么必须采用“一个 Block 负责一行（Block-per-Row）”？

如果在初学者代码中采用朴素的“一个线程负责一行（Thread-per-Row）”： - 线程 0 计算第 0 行，线程 1 计算第 1 行…… - 同一个 Warp 内的 32 个线程在同一时刻读取各自行的第 0 列元素：A[0, 0], A[1, 0], A[2, 0], ...； - 由于是行优先存储，相邻两个元素的内存地址相隔整整 \(N \times 4\) 字节！ - 访存灾难：32 个线程的访存完全离散，硬件无法执行合并访存，被迫拆分为 32 次独立的内存事务，总线有效利用率暴跌至不足 5%！

工业级标准设计采用如图 3-1 所示的 Block-per-Row（一个线程块负责一行矩阵-向量点积）： - 每个 Thread Block（例如 BLOCK_SIZE = 256）专职负责输出向量的一个分量 \(y[\text{row}]\)，即计算第 row = blockIdx.x 行与向量 \(x\) 的内积。 - Block 内的 256 个线程沿着列维度以网格跨步循环前移： cuda for (int col = tid; col < N; col += BLOCK_SIZE) { local_sum += row_A[col] * x[col]; } - 完美访存合并：Warp 内的线程 0 至 31 访问的地址是 row_A[0], row_A[1], ..., row_A[31]，在物理内存上完全连续且天然 128 字节对齐！

B. 向量 \(x\) 的高速片上缓存复用

在计算过程中，所有的 Block（共 \(M\) 个）都需要与同一个向量 \(x\) 相乘。 虽然每个 Block 都从显存中逻辑读取 \(x\)，但由于硬件 L1 Data Cache 和 L2 Cache（几十 MB）的巨大容量，向量 \(x\) 在首个 Block 读取后便大概率常驻在高速片上缓存中，后续各个 Block 读取 \(x\) 几乎全部命中 L2 缓存，极大缓解了显存带宽压力。

C. 点积规约与原子写入解耦（图 3-2）

当 Block 内每个线程完成各自负责列的局部乘累加后，调用第 2 课所学的 block_reduce_sum： 1. Warp 内通过 __shfl_down_sync 快速树状折叠； 2. 跨 Warp 通过 Shared Memory 汇聚为单一标量 sum； 3. 仅由 tid == 0 的单线程将偏置 bias[row] 加上，直接写回全局内存 y[row]。全程无任何原子操作（Atomic-Free），消除了内存争用。

3. 正确性边界与指针安全性

  1. 偏置指针解引用保护：
    • 线性层并非全部带有偏置项（例如现代 LLaMA 架构完全移除了偏置）。
    • 内核代码必须支持 bias == nullptr 的情况：y[row] = sum + (bias ? bias[row] : 0.0f);，严禁无防护直接解引用空指针。
  2. 矩阵维度跨步安全：
    • 当矩阵的行数 \(M\) 大于启动的 Block 数量时，必须依赖网格跨步或确保启动网格充足；
    • 越界检查 if (row >= M) return; 必须放在进入行指针计算的最前端。

4. 性能与工程权舍：何时从 GEMV 转向 GEMM？

  • Block 大小的平衡点：
    • 若列数 \(N\) 较小（例如 \(N=128\)），分配 256 线程会导致一半的线程闲置；
    • 工业级高性能库（如 cuBLAS）会根据 \(N\) 的大小动态调整：当 \(N \le 64\) 时采用 Warp-per-Row（一个 Warp 负责一行），当 \(N \ge 1024\) 时采用 Block-per-Row。
  • 转入 GEMM 的临界点（Prefill vs Decode）：
    • 当并发请求增多，或者进入长 Prompt 预填充阶段（Prefill Phase）时，批次或序列维度 \(B \ge 16 \sim 32\)。
    • 矩阵计算变为 \([M, K] \times [K, B]\)。其算术强度随着 \(B\) 线性提升：\(I \approx \frac{2 M K B}{4(M K + K B + M B)} \gg 10\text{ FLOPs/Byte}\)。
    • 此时内核从访存瓶颈蜕变为算力密集型，必须立即切换为 Tensor Core 驱动的 GEMM 内核（如 CUTLASS / cuBLAS）。

具体演示与数值推演

设矩阵 \(A\) 维度为 \(M = 3\) 行、\(N = 1024\) 列，配置 BLOCK_SIZE = 256，启动发射网格为 <<<3, 256>>>：

  • 硬件映射布局：
    • 系统启动 3 个 Thread Block（Block 0, 1, 2 分别绑定处理 Row 0, 1, 2）。
    • 每个 Block 内驻留 256 个线程（分为 8 个 Warp）。
  • 执行推演（以 Block 0 计算 Row 0 为例）：
    • 单行包含 1024 个列元素，Block 内 256 个线程只需执行 \(\frac{1024}{256} = 4\) 轮循环；
    • 第 1 轮（col = 0 ... 255）：256 个线程合并读取 \(A[0, 0\dots 255]\) 与 \(x[0\dots 255]\)，在寄存器中计算乘积并累加；
    • 第 2~4 轮：线程每次列索引递增 256，继续以连续事务吞吐剩余元素；
    • 4 轮循环结束后，每个线程的私有寄存器 local_sum 中均存有 4 个元素的局部点积和；
    • 调用 block_reduce_sum 进行 256 选 1 的快速折叠，耗时仅几十纳秒；
    • threadIdx.x == 0 线程加上 bias[0]，单次写回 y[0]。
  • 全流程收益：矩阵 \(A\) 的读取 100% 达成 128 字节对齐合并访存，3 行独立输出并行落地。

%%writefile /tmp/03_gemv.cu
#include <cuda_runtime.h>

namespace {

// GEMV 的核心是 dot product，因此 reduce 是主要优化点。
template<int BLOCK_SIZE>
__device__ __forceinline__ float warp_reduce_sum(float val) {
    #pragma unroll
    for (int offset = 16; offset > 0; offset >>= 1) {
        val += __shfl_down_sync(0xffffffff, val, offset);
    }
    return val;
}

// 把一个 block 内所有线程的局部 dot partial sum 合并成一个 sum。
template<int BLOCK_SIZE>
__device__ __forceinline__ float block_reduce_sum(float val) {
    constexpr int NUM_WARPS = (BLOCK_SIZE + 31) / 32;
    __shared__ float smem[NUM_WARPS];

    int lane = threadIdx.x & 31;  //等价于 threadIdx.x % 32
    int warp = threadIdx.x >> 5;  //等价于 threadIdx.x / 32

    val = warp_reduce_sum<BLOCK_SIZE>(val);

    if (lane == 0) {
        smem[warp] = val;
    }
    __syncthreads();

    val = (threadIdx.x < NUM_WARPS) ? smem[lane] : 0.0f;
    if (warp == 0) {
        val = warp_reduce_sum<BLOCK_SIZE>(val);
    }

    __syncthreads();
    return val;
}

// GEMV: y = A * x + bias
// A: [M, N] row-major
// x: [N]
// y/bias: [M]
//
// 简化优化版本：
// 一个 block 负责 A 的一行，block 内线程并行做 dot product。
// 这适合面试讲清楚线程映射、coalesced load、block reduce。
//
// 局限：
// x 会被每一行重复读取。更进一步的优化可以把 x 分块缓存到 shared memory，
// 或者多个 row/block 复用 x tile，但代码会复杂很多。
template<int BLOCK_SIZE>
__global__ void gemv_kernel(
    const float* __restrict__ A,
    const float* __restrict__ x,
    const float* __restrict__ bias,
    float* __restrict__ y,
    int M,
    int N
) {
    int row = blockIdx.x;
    int tid = threadIdx.x;
    if (row >= M) return;

    const float* row_A = A + row * N;
    float local_sum = 0.0f;

    // 每个线程负责这一行里的若干列。
    // A[row, col] 是连续地址，因此一个 warp 同一轮读 A 时是合并访存。
    // x[col] 也是连续读取，但不同 row 会重复读同一个 x。
    for (int col = tid; col < N; col += BLOCK_SIZE) {
        local_sum += ______;  // TODO: 当前列的乘积
    }

    float sum = block_reduce_sum<BLOCK_SIZE>(local_sum);

    // reduce 完后，只有一个线程写 y[row]，避免写冲突。
    if (tid == 0) {
        y[row] = sum + (bias ? bias[row] : 0.0f);
    }
}

} // namespace

void launch_gemv(
    const float* A,
    const float* x,
    const float* bias,
    float* y,
    int M,
    int N,
    cudaStream_t stream
) {
    constexpr int BLOCK_SIZE = 256;
    gemv_kernel<BLOCK_SIZE><<<M, BLOCK_SIZE, 0, stream>>>(
        A, x, bias, y, M, N
    );
}

Q1 参考答案

  • 输入状态：全局显存中连续存储的行优先（Row-Major）矩阵 \(A \in \mathbb{R}^{M \times N}\)、输入向量 \(x \in \mathbb{R}^N\)、可选偏置向量 \(\text{bias} \in \mathbb{R}^M\) 以及启动网格 <<<M, BLOCK_SIZE>>>。
  • 状态变化（行级协同计算流）：
    1. Block 行绑定与指针偏移：每个 Block 由其 blockIdx.x 唯一绑定矩阵的第 row 行，获取行基地址 row_A = A + row * N；
    2. 跨步合并内积：Block 内各线程沿列方向跨步前移（col += BLOCK_SIZE），由于相邻线程访问相邻列元素，完美触发 128 字节对齐合并访存，局部点积累加在寄存器 local_sum 中；
    3. 树状规约汇聚：通过 Warp Shuffle 与 Shared Memory 快速完成 Block 内 256 个局部和的折半规约；
    4. 带偏置单点写回：仅由 tid == 0 线程读取可选的 bias[row]，相加后单次写出到 y[row]。
  • 输出状态：输出向量 \(y\) 的 \(M\) 个分量被 \(M\) 个 Block 并发计算完成，全局内存访问达到接近物理极限的总线利用率。

Q2 参考答案

  • 一线程负责一行（Thread-per-Row）的致命瓶颈：
    • 访存离散（Uncoalesced Memory Access）：同一个 Warp 内的 32 个线程计算 32 个不同行。在行优先存储下，它们在同一拍访问的地址是 A[0, col], A[1, col], ..., A[31, col]，两个地址间距整整相隔 \(N \times 4\) 字节！
    • 带宽雪崩：硬件内存控制器无法合并这些请求，32 个线程产生 32 次独立的非对齐 Cache Line 事务，带宽有效利用率暴跌十倍以上。
  • 一块负责一行（Block-per-Row）的优势与权衡：
    • 优势：同一个 Warp 的 32 个线程共同处理同一行内部的相邻列，A[row, tid] 地址完全连续，天然达成 128 字节合并访存；
    • 代价：行内需要额外的 Block 树状规约开销；若矩阵列数 \(N\) 较小（如 \(N \le 32\)），会出现较多空闲线程，此时更适合采用 Warp-per-Row 策略。

Q3 参考答案

  • 从 GEMV 转向 GEMM 的算术强度拐点：
    • GEMV 的输入批次为 \(B=1\)（单向量），其算术强度上限仅为 \(I \approx 0.5\text{ FLOPs/Byte}\)，性能被全局显存（HBM）带宽牢牢锁死在内存受限区（Memory Bound）；
    • 当并发请求增多、批次合并（Batching）、或在大模型 Prompt 预填充阶段时，批次大小上升至 \(B \ge 16 \sim 32\)。
    • 运算形态演化为矩阵乘矩阵 \([M, K] \times [K, B] \to [M, B]\)。其理论计算量为 \(2 M K B\)，而权重矩阵 \(A\)（\(M \times K\)）被 \(B\) 个样本充分复用，算术强度跃升为： \[I_{\text{GEMM}} \approx \frac{2 M K B}{4(M K + K B + M B)} \gg 10\text{ FLOPs/Byte}\]
    • 此时算子脱离访存受限区，进入 Tensor Core 的高算力受限区（Compute Bound）。必须立即转向利用 Shared Memory 分块缓存与 Tensor Core MMA 指令驱动的 GEMM 内核（如 CUTLASS / cuBLAS）。

### 1. 矩阵-向量乘（GEMV）在大模型推理中的地位与算术强度瓶颈

通用矩阵-向量乘（General Matrix-Vector Multiplication, GEMV: $y = A x + \text{bias}$）是线性代数与深度学习中的基础算子。
尤其在大语言模型（LLM）的**自回归解码生成阶段（Decode Phase）**中，每生成一个新 Token，KV Cache 投影以及 MLP 投影都是以单个 Token（即批次维度 $\text{Batch}=1$）输入线性层。此时通用的矩阵乘（GEMM: $[M, K] \times [K, N]$）必然退化为矩阵-向量乘（GEMV: $[M, N] \times [N, 1] \to [M, 1]$）：
- **极低的算术强度（Memory-Bound 典型代表）**：
  设矩阵 $A \in \mathbb{R}^{M \times N}$，向量 $x \in \mathbb{R}^N$。
  - 理论计算量：每个元素需要 1 次乘法和 1 次加法，总浮点运算量为 $2 M N\text{ FLOPs}$；
  - 显存访存量：必须从全局内存中加载整个权重矩阵 $A$（$4MN$ 字节），读取向量 $x$（$4N$ 字节），并写回结果 $y$（$4M$ 字节）。
  - 其算术强度上限仅为：
    $$I = \frac{2 M N}{4 M N + 4 N + 4 M} \approx \frac{2 M N}{4 M N} = 0.5 \text{ FLOPs/Byte}$$
  在标称带宽 $3.35\text{ TB/s}$ 的 H100 GPU 上，GEMV 的理论算力上限只有 $\approx 1.67\text{ TFLOPS}$（远低于硬件 $1000\text{ TFLOPS}$ 峰值）。
  因此，GEMV 的优化哲学在于：**极致榨干全局显存读取带宽，确保权重矩阵 $A$ 的合并访存，并最大化向量 $x$ 在 L1/L2 缓存中的数据复用**。

### 2. 行级并行与 Block 映射架构（如**图 3-1** 与**图 3-2** 所示）

在行优先（Row-Major）存储格式下，矩阵 $A$ 的同一行元素在物理内存地址中是严格连续排列的。

#### A. 为什么必须采用“一个 Block 负责一行（Block-per-Row）”？
如果在初学者代码中采用朴素的“一个线程负责一行（Thread-per-Row）”：
- 线程 0 计算第 0 行，线程 1 计算第 1 行……
- 同一个 Warp 内的 32 个线程在同一时刻读取各自行的第 0 列元素：`A[0, 0], A[1, 0], A[2, 0], ...`；
- 由于是行优先存储，相邻两个元素的内存地址相隔整整 $N \times 4$ 字节！
- **访存灾难**：32 个线程的访存完全离散，硬件无法执行合并访存，被迫拆分为 32 次独立的内存事务，总线有效利用率暴跌至不足 5%！

工业级标准设计采用如**图 3-1** 所示的 **Block-per-Row（一个线程块负责一行矩阵-向量点积）**：
- 每个 Thread Block（例如 `BLOCK_SIZE = 256`）专职负责输出向量的一个分量 $y[\text{row}]$，即计算第 `row = blockIdx.x` 行与向量 $x$ 的内积。
- Block 内的 256 个线程沿着列维度以网格跨步循环前移：
  ```cuda
  for (int col = tid; col < N; col += BLOCK_SIZE) {
      local_sum += row_A[col] * x[col];
  }
  ```
- **完美访存合并**：Warp 内的线程 0 至 31 访问的地址是 `row_A[0], row_A[1], ..., row_A[31]`，在物理内存上**完全连续且天然 128 字节对齐**！

#### B. 向量 $x$ 的高速片上缓存复用
在计算过程中，所有的 Block（共 $M$ 个）都需要与同一个向量 $x$ 相乘。
虽然每个 Block 都从显存中逻辑读取 $x$，但由于硬件 L1 Data Cache 和 L2 Cache（几十 MB）的巨大容量，向量 $x$ 在首个 Block 读取后便大概率常驻在高速片上缓存中，后续各个 Block 读取 $x$ 几乎全部命中 L2 缓存，极大缓解了显存带宽压力。

#### C. 点积规约与原子写入解耦（图 3-2）
当 Block 内每个线程完成各自负责列的局部乘累加后，调用第 2 课所学的 `block_reduce_sum`：
1. Warp 内通过 `__shfl_down_sync` 快速树状折叠；
2. 跨 Warp 通过 Shared Memory 汇聚为单一标量 `sum`；
3. 仅由 `tid == 0` 的单线程将偏置 `bias[row]` 加上，直接写回全局内存 `y[row]`。全程**无任何原子操作（Atomic-Free）**，消除了内存争用。

### 3. 正确性边界与指针安全性

1. **偏置指针解引用保护**：
   - 线性层并非全部带有偏置项（例如现代 LLaMA 架构完全移除了偏置）。
   - 内核代码必须支持 `bias == nullptr` 的情况：`y[row] = sum + (bias ? bias[row] : 0.0f);`，严禁无防护直接解引用空指针。
2. **矩阵维度跨步安全**：
   - 当矩阵的行数 $M$ 大于启动的 Block 数量时，必须依赖网格跨步或确保启动网格充足；
   - 越界检查 `if (row >= M) return;` 必须放在进入行指针计算的最前端。

### 4. 性能与工程权舍：何时从 GEMV 转向 GEMM？

- **Block 大小的平衡点**：
  - 若列数 $N$ 较小（例如 $N=128$），分配 256 线程会导致一半的线程闲置；
  - 工业级高性能库（如 cuBLAS）会根据 $N$ 的大小动态调整：当 $N \le 64$ 时采用 Warp-per-Row（一个 Warp 负责一行），当 $N \ge 1024$ 时采用 Block-per-Row。
- **转入 GEMM 的临界点（Prefill vs Decode）**：
  - 当并发请求增多，或者进入长 Prompt 预填充阶段（Prefill Phase）时，批次或序列维度 $B \ge 16 \sim 32$。
  - 矩阵计算变为 $[M, K] \times [K, B]$。其算术强度随着 $B$ 线性提升：$I \approx \frac{2 M K B}{4(M K + K B + M B)} \gg 10\text{ FLOPs/Byte}$。
  - 此时内核从访存瓶颈蜕变为算力密集型，必须立即切换为 Tensor Core 驱动的 GEMM 内核（如 CUTLASS / cuBLAS）。

## 具体演示与数值推演

设矩阵 $A$ 维度为 $M = 3$ 行、$N = 1024$ 列，配置 `BLOCK_SIZE = 256`，启动发射网格为 `<<<3, 256>>>`：

- **硬件映射布局**：
  - 系统启动 3 个 Thread Block（Block 0, 1, 2 分别绑定处理 Row 0, 1, 2）。
  - 每个 Block 内驻留 256 个线程（分为 8 个 Warp）。
- **执行推演（以 Block 0 计算 Row 0 为例）**：
  - 单行包含 1024 个列元素，Block 内 256 个线程只需执行 $\frac{1024}{256} = 4$ 轮循环；
  - **第 1 轮（`col = 0 ... 255`）**：256 个线程合并读取 $A[0, 0\dots 255]$ 与 $x[0\dots 255]$，在寄存器中计算乘积并累加；
  - **第 2~4 轮**：线程每次列索引递增 256，继续以连续事务吞吐剩余元素；
  - 4 轮循环结束后，每个线程的私有寄存器 `local_sum` 中均存有 4 个元素的局部点积和；
  - 调用 `block_reduce_sum` 进行 256 选 1 的快速折叠，耗时仅几十纳秒；
  - `threadIdx.x == 0` 线程加上 `bias[0]`，单次写回 `y[0]`。
- **全流程收益**：矩阵 $A$ 的读取 100% 达成 128 字节对齐合并访存，3 行独立输出并行落地。

__device__ __forceinline__ float warp_reduce_sum(float val) {
    #pragma unroll
    for (int offset = 16; offset > 0; offset >>= 1) {
        val += __shfl_down_sync(0xffffffff, val, offset);
    }
    return val;
}

__device__ __forceinline__ float block_reduce_sum(float val) {
    constexpr int NUM_WARPS = (BLOCK_SIZE + 31) / 32;
    __shared__ float smem[NUM_WARPS];

    int lane = threadIdx.x & 31;  //等价于 threadIdx.x % 32

    if (lane == 0) {
        smem[warp] = val;
    }
    __syncthreads();

    val = (threadIdx.x < NUM_WARPS) ? smem[lane] : 0.0f;
    if (warp == 0) {
        val = warp_reduce_sum<BLOCK_SIZE>(val);
    }

    __syncthreads();
    return val;
}

    // x[col] 也是连续读取，但不同 row 会重复读同一个 x。

- **输入状态**：全局显存中连续存储的行优先（Row-Major）矩阵 $A \in \mathbb{R}^{M \times N}$、输入向量 $x \in \mathbb{R}^N$、可选偏置向量 $\text{bias} \in \mathbb{R}^M$ 以及启动网格 `<<<M, BLOCK_SIZE>>>`。
- **状态变化（行级协同计算流）**：
  1. **Block 行绑定与指针偏移**：每个 Block 由其 `blockIdx.x` 唯一绑定矩阵的第 `row` 行，获取行基地址 `row_A = A + row * N`；
  2. **跨步合并内积**：Block 内各线程沿列方向跨步前移（`col += BLOCK_SIZE`），由于相邻线程访问相邻列元素，完美触发 128 字节对齐合并访存，局部点积累加在寄存器 `local_sum` 中；
  3. **树状规约汇聚**：通过 Warp Shuffle 与 Shared Memory 快速完成 Block 内 256 个局部和的折半规约；
  4. **带偏置单点写回**：仅由 `tid == 0` 线程读取可选的 `bias[row]`，相加后单次写出到 `y[row]`。
- **输出状态**：输出向量 $y$ 的 $M$ 个分量被 $M$ 个 Block 并发计算完成，全局内存访问达到接近物理极限的总线利用率。

### Q2 参考答案

- **一线程负责一行（Thread-per-Row）的致命瓶颈**：
  - *访存离散（Uncoalesced Memory Access）*：同一个 Warp 内的 32 个线程计算 32 个不同行。在行优先存储下，它们在同一拍访问的地址是 `A[0, col], A[1, col], ..., A[31, col]`，两个地址间距整整相隔 $N \times 4$ 字节！
  - *带宽雪崩*：硬件内存控制器无法合并这些请求，32 个线程产生 32 次独立的非对齐 Cache Line 事务，带宽有效利用率暴跌十倍以上。
- **一块负责一行（Block-per-Row）的优势与权衡**：
  - *优势*：同一个 Warp 的 32 个线程共同处理同一行内部的相邻列，`A[row, tid]` 地址完全连续，天然达成 128 字节合并访存；
  - *代价*：行内需要额外的 Block 树状规约开销；若矩阵列数 $N$ 较小（如 $N \le 32$），会出现较多空闲线程，此时更适合采用 Warp-per-Row 策略。

### Q3 参考答案

- **从 GEMV 转向 GEMM 的算术强度拐点**：
  - GEMV 的输入批次为 $B=1$（单向量），其算术强度上限仅为 $I \approx 0.5\text{ FLOPs/Byte}$，性能被全局显存（HBM）带宽牢牢锁死在内存受限区（Memory Bound）；
  - 当并发请求增多、批次合并（Batching）、或在大模型 Prompt 预填充阶段时，批次大小上升至 $B \ge 16 \sim 32$。
  - 运算形态演化为矩阵乘矩阵 $[M, K] \times [K, B] \to [M, B]$。其理论计算量为 $2 M K B$，而权重矩阵 $A$（$M \times K$）被 $B$ 个样本充分复用，算术强度跃升为：
    $$I_{\text{GEMM}} \approx \frac{2 M K B}{4(M K + K B + M B)} \gg 10\text{ FLOPs/Byte}$$
  - 此时算子脱离访存受限区，进入 Tensor Core 的高算力受限区（Compute Bound）。必须立即转向利用 Shared Memory 分块缓存与 Tensor Core MMA 指令驱动的 GEMM 内核（如 CUTLASS / cuBLAS）。
