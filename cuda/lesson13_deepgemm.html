1. 它是什么，解决什么问题

DeepGEMM 是 DeepSeek 专为大语言模型（特别是 DeepSeek-V3 / V2.5 / R1 等超大规模 MoE 模型）研发的开源超高性能 Tensor Core GEMM 算子库。

(1) 为什么现有开源库（CUTLASS 3.x / cuBLASLt）不够用？

  1. CUTLASS 3.x 极其庞大的 C++ 模板膨胀与编译噩梦：
    • 传统 CUTLASS 依赖极深的模板嵌套与代数表达（Layout、Tile、Iterator、Collective Builder），仅编译一组 GEMM 内核通常需要数分钟乃至数十分钟；
    • 工业级二次开发、定制特殊访存或微架构调优时，工程师深陷模板推导黑洞，调试门槛极高。
  2. DeepSeek-V3 细粒度分块量化（\(1 \times 128\) Block-wise FP8）缺乏原生极致优化：
    • 常规 TensorRT-LLM 或 cuBLASLt 主要面向 Tensor-wise（整张量单标量缩放） 或 Channel-wise（逐通道缩放）；
    • DeepSeek-V3 为了在 FP8 下保持与 BF16 无损的数学精度，提出了 \(1 \times 128\) 的 Block-wise Fine-grained Scaling：矩阵在 \(K\) 维度每 128 个元素划分为一个独立 Block，拥有专属的 FP32/UE8M0 缩放系数。这要求 GEMM 内核的 Epilogue 必须在极短时间内完成多维缩放反量化，cuBLASLt 无法原生内联融合。
  3. MoE 解码（Decoding）与 CUDA Graph 的静态分配冲突：
    • 在推理 Decode 阶段，各 Expert 分配到的 Token 数量极小且每步动态变化；
    • 若使用传统变长 Grouped GEMM，CPU 必须每步重新统计各专家 Token 偏移量并下发 Kernel 参数，彻底打破 CUDA Graph 捕获机制，带来沉重的 CPU Launch 延迟。

(2) DeepGEMM 的破局设计

  • Radical KISS 原则：完全摒弃 CUTLASS 繁重的类层次结构，精炼出不到数千行的自包含代码，通过轻量级 C++ JIT（即时编译）模块在运行时极速加载，免去安装时的预编译开销；
  • 原生拥抱 Hopper 硬件原语：深度利用 SM90 硬件级 TMA（张量内存加速器）与 WGMMA 指令，在 H800/H100 上跑出高达 1550 TFLOPS（逼近硬件理论极限的 85%~90%）；
  • 双模 MoE Grouped GEMM 支持：
    • Contiguous：用于训练前向/反向与推理 Prefill，连续内存拼接，算力利用率最大化；
    • Masked：用于推理 Decode，配合 DeepEP 零 CPU 开销静态捕获，以 Mask 标记有效 Token，完全兼容 CUDA Graph。

2. Hopper (SM90) 硬件微架构机制剖析

要真正看懂 DeepGEMM 的源码，必须理解 Hopper 架构相对于 Ampere 架构发生的三大革命性跃迁：

(1) TMA (Tensor Memory Accelerator)：异步硬件批量搬运

  • Ampere 痛点：在 Ampere（SM80）中，虽然引入了 cp.async，但每个线程仍需显式计算地址偏移，执行指令发射。
  • Hopper 创新：TMA 是片上独立的专用硬件单元。线程只需配置一个 cute::TmaDescriptor（包含张量基地址、形状、跨度、分块尺寸及 Swizzle 模式），随后仅需由单个线程发起一条 cp.async.bulk.tensor 指令，硬件直接将多维张量瓦片从全局显存（Global Memory）搬运至共享内存（Shared Memory），全程完全不占用 SM 通用寄存器和 ALU 算力！

(2) WGMMA (wgmma.mma_async)：Warp-Group 级异步矩阵乘

  • Ampere 痛点：mma.sync 是 Warp 级同步指令，线程必须先从 SMEM 把数据显式 ldmatrix 加载到通用寄存器（Register File），消耗大量寄存器配额，极易导致寄存器溢出（Spilling）而降低 Occupancy。
  • Hopper 创新：WGMMA 提升至 Warp-Group（4 个 Warp，共 128 个线程） 协同粒度。更关键的是，它支持 SS（Shared-Shared）寻址模式：Tensor Core 直接从 Shared Memory 读取矩阵 A 与矩阵 B 的切片执行点积，中间完全跳过通用寄存器！仅输出累加矩阵 \(D\) 保存在 FP32 寄存器中，极大节省了片上寄存器开销。

(3) 生产者-消费者解耦（Producer-Consumer Splitting）与 mbarrier

DeepGEMM 将一个 ThreadBlock（例如 256 或 384 线程）进行角色解耦： - 生产者（TMA Warp-Group，128 线程）：负责调度 TMA 硬件发起下一阶段的 A、B 及 Scale Factor 数据预取，并在硬件事务屏障（ClusterTransactionBarrier）上注册预期传输字节数（expect_tx）； - 消费者（Math Warp-Groups，128 或 256 线程）：通过 mbarrier.try_wait.parity 轮询硬件屏障。一旦 TMA 数据到位，立即执行 wgmma.mma_async，实现极致的多级流水掩盖（\(k\text{NumStages} = 3 \sim 4\)）。

3. DeepGEMM 核心代码架构逐行拆解

以下代码节选自 DeepGEMM 核心源码 sm90_fp8_gemm_1d1d.cuh，展现其关键骨架：

// DeepGEMM: TMA 与 WGMMA 核心主循环骨架
#pragma once
#include <deep_gemm/ptx/tma.cuh>
#include <deep_gemm/ptx/wgmma.cuh>

template <uint32_t BLOCK_M, uint32_t BLOCK_N, uint32_t BLOCK_K, uint32_t kNumStages>
__device__ void gemm_loop(
    const cute::TmaDescriptor& tensor_map_a,
    const cute::TmaDescriptor& tensor_map_b,
    float* smem_sfa, float* smem_sfb,
    uint32_t k_tiles) {

    // 1. 硬件事务屏障初始化
    extern __shared__ char smem_raw[];
    auto* barriers = reinterpret_cast<cutlass::arch::ClusterTransactionBarrier*>(smem_raw);

    // 2. 区分生产者（TMA）与消费者（Math）
    const uint32_t warp_group_idx = threadIdx.x / 128;
    const bool is_producer = (warp_group_idx == 0);

    #pragma unroll 1
    for (uint32_t k = 0; k < k_tiles; ++k) {
        uint32_t stage = k % kNumStages;

        if (is_producer && threadIdx.x == 0) {
            // 生产者主线程：设置本阶段期望接收的 TMA 字节数
            uint32_t tx_bytes = (BLOCK_M * BLOCK_K + BLOCK_N * BLOCK_K) * sizeof(__nv_fp8_e4m3);
            ptx::mbarrier_arrive_and_set_tx(&barriers[stage], tx_bytes);

            // 发起 TMA 异步多维拷贝
            ptx::tma_copy_2d(tensor_map_a, &barriers[stage], stage, k);
            ptx::tma_copy_2d(tensor_map_b, &barriers[stage], stage, k);
        }

        if (!is_producer) {
            // 消费者：等待当前 Stage 数据加载完毕（硬件屏障就绪）
            ptx::mbarrier_wait(&barriers[stage], k / kNumStages);

            // 消费者：发射 WGMMA 指令（SS 模式：直接自 SMEM 计算并累加到寄存器 D）
            wgmma::FP8MMA<BLOCK_N>::wgmma(
                desc_a[stage], desc_b[stage], accum_d, /*scale_d=*/(k != 0)
            );
        }
    }
}

def fine_grained_block_gemm_simulation(A_fp8, B_fp8, S_A, S_B, block_k=128):

Q1 参考答案

  1. 数值精度与动态范围（Dynamic Range）： FP8（E4M3 格式）的有效动态范围极小（仅 8 个指数位与尾数位，绝对值最大仅 448，精度显著低于 BF16/FP16）。大模型各激活通道间存在严重的离群值（Outliers）。若采用 Tensor-wise 单一缩放因子，为了容纳极大离群值，缩放系数必须非常大，导致绝大多数正常数值下溢变为 0，引起灾难性精度崩塌。\(1 \times 128\) 细粒度分块量化将缩放局限在 128 个 Channel 内部，实现了极高的局部信噪比。
  2. 对 Hopper WGMMA 的挑战： 标准 WGMMA 的累加器工作在数学上的连续点积模式。在 \(1 \times 128\) 模式下，点积不能无休止地在一个循环内跨 Block 累加，或者必须在 Epilogue 阶段将乘积拆解。DeepGEMM 的极致优化在于：将 \(K\) 维分块瓦片大小（BLOCK_K）精准绑定为 \(128\)。每个 WGMMA 刚好计算完这 128 个元素后，由消费者线程直接在寄存器中乘以对应的 Scale_A * Scale_B，使得点积累加与反量化严格同步，杜绝了中间精度的溢出。

Q2 参考答案

  1. 彻底消除寄存器往返搬运（Zero Register Allocation for Operands）： Ampere 的流程是：Global Memory -> (cp.async) -> SMEM -> (ldmatrix) -> Registers -> (mma.sync) -> Registers。A 和 B 矩阵必须同时常驻在寄存器堆中，每个线程需要几十甚至上百个寄存器存放输入操作数。 Hopper WGMMA 的 SS 模式是：Global Memory -> (TMA) -> SMEM -> (wgmma.mma_async) -> Registers(仅存放累加器 D)。矩阵 A 和 B 的输入操作数永远停留在 SMEM，Tensor Core 直接通过硬件总线并发抓取 SMEM 数据进行 FMA。
  2. 性能与 Occupancy 飞跃： 寄存器占用量骤降 60% 以上，使得每个 SM 可以容纳更多并发活跃的 ThreadBlock（提升 Occupancy）。同时完全消除了 ldmatrix 指令的发射开销，解除了 Warp Scheduler 的指令发射槽瓶颈。

Q3 参考答案

  1. CUDA Graph 核心不变性原理： CUDA Graph 依赖“静态执行图”消除 CPU Launch 开销。在 Graph 捕获期间，所有 Kernel 的 Launch 参数、输入输出指针、Grid/Block 维度必须完全固化，执行期不得发起任何主机端动态内存分配或 CPU-GPU 间的同步（如根据各专家实际 Token 偏移重算元数据）。
  2. Masked 布局解决动态偏移： 在 Decode 阶段，每个 GPU 每步分配给各个 Expert 的 Token 数完全动态不可预知。m_grouped_fp8_gemm_nt_masked 预先分配满足最大并发 Token 长度的静态 Buffer。通信库 DeepEP 将收到的数据直接散列在固定 Slot 中，并生成一份 0/1 Mask 张量。Kernel 在执行时遍历固定网格，仅在 mask[token] == 1 时执行真实计算，跳过无效分块，在完全不打断 CUDA Graph 静态回放的前提下完美适配 MoE 动态路由。

面试高频追问与工业级优化扩展

  • 追问 1：TMA 的 Multicast 广播特性在 GEMM 中如何使用？
    • 回答要点：Hopper 引入了 Cluster 概念（最多 8 个 SM 组成硬件集群）。当多个 SM 负责计算相同 \(M\) 或相同 \(N\) 维度的矩阵瓦片时，A 或 B 矩阵数据完全相同。TMA 支持 Cluster Multicast：一个 SM 发起 TMA 读取，硬件可将数据自动多播并发写入集群内其他多个 SM 的 Shared Memory 中，将 L2 Cache 和显存带宽压力直接骤降数倍！
  • 追问 2：为什么 DeepGEMM 坚决不用 NVRTC 而是自研 C++ JIT 编译系统？
    • 回答要点：早期版本尝试过 NVRTC，但发现 NVRTC 针对 Hopper SM90 高级 PTX（如 WGMMA、TMA 事务屏障）的代码生成效率和指令交织优化远不如最新的标准 NVCC 驱动编译器。DeepGEMM 开发了轻量级的 C++ JIT 运行时，直接调用主机端 NVCC 缓存二进制产物，实现了亚秒级冷启动与极低运行时调用开销。

### 1. 它是什么，解决什么问题

**DeepGEMM** 是 DeepSeek 专为大语言模型（特别是 DeepSeek-V3 / V2.5 / R1 等超大规模 MoE 模型）研发的开源超高性能 Tensor Core GEMM 算子库。

#### (1) 为什么现有开源库（CUTLASS 3.x / cuBLASLt）不够用？
1. **CUTLASS 3.x 极其庞大的 C++ 模板膨胀与编译噩梦**：
   - 传统 CUTLASS 依赖极深的模板嵌套与代数表达（Layout、Tile、Iterator、Collective Builder），仅编译一组 GEMM 内核通常需要数分钟乃至数十分钟；
   - 工业级二次开发、定制特殊访存或微架构调优时，工程师深陷模板推导黑洞，调试门槛极高。
2. **DeepSeek-V3 细粒度分块量化（$1 \times 128$ Block-wise FP8）缺乏原生极致优化**：
   - 常规 TensorRT-LLM 或 cuBLASLt 主要面向 **Tensor-wise（整张量单标量缩放）** 或 **Channel-wise（逐通道缩放）**；
   - DeepSeek-V3 为了在 FP8 下保持与 BF16 无损的数学精度，提出了 **$1 \times 128$ 的 Block-wise Fine-grained Scaling**：矩阵在 $K$ 维度每 128 个元素划分为一个独立 Block，拥有专属的 FP32/UE8M0 缩放系数。这要求 GEMM 内核的 Epilogue 必须在极短时间内完成多维缩放反量化，cuBLASLt 无法原生内联融合。
3. **MoE 解码（Decoding）与 CUDA Graph 的静态分配冲突**：
   - 在推理 Decode 阶段，各 Expert 分配到的 Token 数量极小且每步动态变化；
   - 若使用传统变长 Grouped GEMM，CPU 必须每步重新统计各专家 Token 偏移量并下发 Kernel 参数，**彻底打破 CUDA Graph 捕获机制**，带来沉重的 CPU Launch 延迟。

#### (2) DeepGEMM 的破局设计
- **Radical KISS 原则**：完全摒弃 CUTLASS 繁重的类层次结构，精炼出不到数千行的自包含代码，通过轻量级 C++ JIT（即时编译）模块在运行时极速加载，免去安装时的预编译开销；
- **原生拥抱 Hopper 硬件原语**：深度利用 SM90 硬件级 TMA（张量内存加速器）与 WGMMA 指令，在 H800/H100 上跑出高达 **1550 TFLOPS（逼近硬件理论极限的 85%~90%）**；
- **双模 MoE Grouped GEMM 支持**：
  - `Contiguous`：用于训练前向/反向与推理 Prefill，连续内存拼接，算力利用率最大化；
  - `Masked`：用于推理 Decode，配合 DeepEP 零 CPU 开销静态捕获，以 Mask 标记有效 Token，完全兼容 CUDA Graph。

### 2. Hopper (SM90) 硬件微架构机制剖析

要真正看懂 DeepGEMM 的源码，必须理解 Hopper 架构相对于 Ampere 架构发生的三大革命性跃迁：

#### (1) TMA (Tensor Memory Accelerator)：异步硬件批量搬运
- **Ampere 痛点**：在 Ampere（SM80）中，虽然引入了 `cp.async`，但每个线程仍需显式计算地址偏移，执行指令发射。
- **Hopper 创新**：TMA 是片上独立的专用硬件单元。线程只需配置一个 `cute::TmaDescriptor`（包含张量基地址、形状、跨度、分块尺寸及 Swizzle 模式），随后仅需由单个线程发起一条 `cp.async.bulk.tensor` 指令，硬件直接将多维张量瓦片从全局显存（Global Memory）搬运至共享内存（Shared Memory），**全程完全不占用 SM 通用寄存器和 ALU 算力**！

#### (2) WGMMA (`wgmma.mma_async`)：Warp-Group 级异步矩阵乘
- **Ampere 痛点**：`mma.sync` 是 Warp 级同步指令，线程必须先从 SMEM 把数据显式 `ldmatrix` 加载到通用寄存器（Register File），消耗大量寄存器配额，极易导致寄存器溢出（Spilling）而降低 Occupancy。
- **Hopper 创新**：WGMMA 提升至 **Warp-Group（4 个 Warp，共 128 个线程）** 协同粒度。更关键的是，它支持 **SS（Shared-Shared）寻址模式**：Tensor Core 直接从 Shared Memory 读取矩阵 A 与矩阵 B 的切片执行点积，**中间完全跳过通用寄存器**！仅输出累加矩阵 $D$ 保存在 FP32 寄存器中，极大节省了片上寄存器开销。

#### (3) 生产者-消费者解耦（Producer-Consumer Splitting）与 `mbarrier`
DeepGEMM 将一个 ThreadBlock（例如 256 或 384 线程）进行角色解耦：
- **生产者（TMA Warp-Group，128 线程）**：负责调度 TMA 硬件发起下一阶段的 A、B 及 Scale Factor 数据预取，并在硬件事务屏障（`ClusterTransactionBarrier`）上注册预期传输字节数（`expect_tx`）；
- **消费者（Math Warp-Groups，128 或 256 线程）**：通过 `mbarrier.try_wait.parity` 轮询硬件屏障。一旦 TMA 数据到位，立即执行 `wgmma.mma_async`，实现极致的多级流水掩盖（$k\text{NumStages} = 3 \sim 4$）。

### 3. DeepGEMM 核心代码架构逐行拆解

以下代码节选自 DeepGEMM 核心源码 [`sm90_fp8_gemm_1d1d.cuh`](file:///Users/wujie/hpclearning/cuda/DeepGEMM/deep_gemm/include/deep_gemm/impls/sm90_fp8_gemm_1d1d.cuh)，展现其关键骨架：

```cuda
// DeepGEMM: TMA 与 WGMMA 核心主循环骨架
#pragma once
#include <deep_gemm/ptx/tma.cuh>
#include <deep_gemm/ptx/wgmma.cuh>

template <uint32_t BLOCK_M, uint32_t BLOCK_N, uint32_t BLOCK_K, uint32_t kNumStages>
__device__ void gemm_loop(
    const cute::TmaDescriptor& tensor_map_a,
    const cute::TmaDescriptor& tensor_map_b,
    float* smem_sfa, float* smem_sfb,
    uint32_t k_tiles) {

    // 1. 硬件事务屏障初始化
    extern __shared__ char smem_raw[];
    auto* barriers = reinterpret_cast<cutlass::arch::ClusterTransactionBarrier*>(smem_raw);

    // 2. 区分生产者（TMA）与消费者（Math）
    const uint32_t warp_group_idx = threadIdx.x / 128;
    const bool is_producer = (warp_group_idx == 0);

    #pragma unroll 1
    for (uint32_t k = 0; k < k_tiles; ++k) {
        uint32_t stage = k % kNumStages;

        if (is_producer && threadIdx.x == 0) {
            // 生产者主线程：设置本阶段期望接收的 TMA 字节数
            uint32_t tx_bytes = (BLOCK_M * BLOCK_K + BLOCK_N * BLOCK_K) * sizeof(__nv_fp8_e4m3);
            ptx::mbarrier_arrive_and_set_tx(&barriers[stage], tx_bytes);

            // 发起 TMA 异步多维拷贝
            ptx::tma_copy_2d(tensor_map_a, &barriers[stage], stage, k);
            ptx::tma_copy_2d(tensor_map_b, &barriers[stage], stage, k);
        }

        if (!is_producer) {
            // 消费者：等待当前 Stage 数据加载完毕（硬件屏障就绪）
            ptx::mbarrier_wait(&barriers[stage], k / kNumStages);

            // 消费者：发射 WGMMA 指令（SS 模式：直接自 SMEM 计算并累加到寄存器 D）
            wgmma::FP8MMA<BLOCK_N>::wgmma(
                desc_a[stage], desc_b[stage], accum_d, /*scale_d=*/(k != 0)
            );
        }
    }
}
```

def fine_grained_block_gemm_simulation(A_fp8, B_fp8, S_A, S_B, block_k=128):
    M, K = A_fp8.shape
    N, K_b = B_fp8.shape
    assert K == K_b, "K dimension mismatch"
    assert K % block_k == 0, "K must be divisible by block_k"
    num_blocks = K // block_k
    
    D = np.zeros((M, N), dtype=np.float32)
    
    for b in range(num_blocks):
        k_start = b * block_k
        k_end = (b + 1) * block_k
        
        # 提取当前 128-channel 瓦片
        A_tile = A_fp8[:, k_start:k_end]  # [M, block_k]
        B_tile = B_fp8[:, k_start:k_end]  # [N, block_k]
        
        # 1. 执行片上 Tile 点积累加
        tile_acc = np.matmul(A_tile, B_tile.T)
        
        # 2. 提取当前 Block 的缩放因子外积 (利用广播生成 [M, N])
        scale_tile = S_A[:, b:b+1] * S_B[:, b:b+1].T
        
        # 3. 反量化并累加
        D += tile_acc * scale_tile
        
    return D

# 执行验证

### Q1 参考答案

1. **数值精度与动态范围（Dynamic Range）**：
   FP8（E4M3 格式）的有效动态范围极小（仅 8 个指数位与尾数位，绝对值最大仅 448，精度显著低于 BF16/FP16）。大模型各激活通道间存在严重的离群值（Outliers）。若采用 Tensor-wise 单一缩放因子，为了容纳极大离群值，缩放系数必须非常大，导致绝大多数正常数值下溢变为 0，引起灾难性精度崩塌。$1 \times 128$ 细粒度分块量化将缩放局限在 128 个 Channel 内部，实现了极高的局部信噪比。
2. **对 Hopper WGMMA 的挑战**：
   标准 WGMMA 的累加器工作在数学上的连续点积模式。在 $1 \times 128$ 模式下，点积不能无休止地在一个循环内跨 Block 累加，或者必须在 Epilogue 阶段将乘积拆解。DeepGEMM 的极致优化在于：将 $K$ 维分块瓦片大小（`BLOCK_K`）精准绑定为 $128$。每个 WGMMA 刚好计算完这 128 个元素后，由消费者线程直接在寄存器中乘以对应的 `Scale_A * Scale_B`，使得点积累加与反量化严格同步，杜绝了中间精度的溢出。

### Q2 参考答案

1. **彻底消除寄存器往返搬运（Zero Register Allocation for Operands）**：
   Ampere 的流程是：`Global Memory -> (cp.async) -> SMEM -> (ldmatrix) -> Registers -> (mma.sync) -> Registers`。A 和 B 矩阵必须同时常驻在寄存器堆中，每个线程需要几十甚至上百个寄存器存放输入操作数。
   Hopper WGMMA 的 SS 模式是：`Global Memory -> (TMA) -> SMEM -> (wgmma.mma_async) -> Registers(仅存放累加器 D)`。矩阵 A 和 B 的输入操作数永远停留在 SMEM，Tensor Core 直接通过硬件总线并发抓取 SMEM 数据进行 FMA。
2. **性能与 Occupancy 飞跃**：
   寄存器占用量骤降 60% 以上，使得每个 SM 可以容纳更多并发活跃的 ThreadBlock（提升 Occupancy）。同时完全消除了 `ldmatrix` 指令的发射开销，解除了 Warp Scheduler 的指令发射槽瓶颈。

### Q3 参考答案

1. **CUDA Graph 核心不变性原理**：
   CUDA Graph 依赖“静态执行图”消除 CPU Launch 开销。在 Graph 捕获期间，所有 Kernel 的 Launch 参数、输入输出指针、Grid/Block 维度必须完全固化，执行期不得发起任何主机端动态内存分配或 CPU-GPU 间的同步（如根据各专家实际 Token 偏移重算元数据）。
2. **Masked 布局解决动态偏移**：
   在 Decode 阶段，每个 GPU 每步分配给各个 Expert 的 Token 数完全动态不可预知。`m_grouped_fp8_gemm_nt_masked` 预先分配满足最大并发 Token 长度的静态 Buffer。通信库 DeepEP 将收到的数据直接散列在固定 Slot 中，并生成一份 0/1 Mask 张量。Kernel 在执行时遍历固定网格，仅在 `mask[token] == 1` 时执行真实计算，跳过无效分块，在完全不打断 CUDA Graph 静态回放的前提下完美适配 MoE 动态路由。

## 面试高频追问与工业级优化扩展

- **追问 1：TMA 的 Multicast 广播特性在 GEMM 中如何使用？**
  - *回答要点*：Hopper 引入了 Cluster 概念（最多 8 个 SM 组成硬件集群）。当多个 SM 负责计算相同 $M$ 或相同 $N$ 维度的矩阵瓦片时，A 或 B 矩阵数据完全相同。TMA 支持 Cluster Multicast：一个 SM 发起 TMA 读取，硬件可将数据自动多播并发写入集群内其他多个 SM 的 Shared Memory 中，将 L2 Cache 和显存带宽压力直接骤降数倍！
- **追问 2：为什么 DeepGEMM 坚决不用 NVRTC 而是自研 C++ JIT 编译系统？**
  - *回答要点*：早期版本尝试过 NVRTC，但发现 NVRTC 针对 Hopper SM90 高级 PTX（如 WGMMA、TMA 事务屏障）的代码生成效率和指令交织优化远不如最新的标准 NVCC 驱动编译器。DeepGEMM 开发了轻量级的 C++ JIT 运行时，直接调用主机端 NVCC 缓存二进制产物，实现了亚秒级冷启动与极低运行时调用开销。
