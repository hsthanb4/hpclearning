1. 它是什么，解决什么问题

CUTLASS（CUDA Templates for Linear Algebra Subroutines） 是 NVIDIA 开源的高性能 CUDA C++ 模板抽象库，其 3.x 版本引入了 CuTe（C++ Layout Algebra） 体系。它专为榨干 Volta、Turing、Ampere、Ada、Hopper 以及 Blackwell 各代 GPU 的 Tensor Core 极限算力而生。

GPU 硬件的深层物理矛盾与解决之道（结合图 1-1 与图 1-2）： - 算力与显存带宽的万倍鸿沟：以 NVIDIA H100 为例，BF16 稠密矩阵算力峰值接近 \(1000 \text{ TFLOPS}\)，而 HBM3 显存带宽仅为 \(3.35 \text{ TB/s}\)。若每个乘加指令都需要从 HBM 提取操作数，硬件算力利用率将不足 1%； - 存储金字塔与分层复用（图 1-2）：GPU 拥有三级核心存储层次： 1. 全局显存（Global Memory / HBM）：容量大（80~144 GB），但延迟高（数百时钟周期）、带宽相对较窄； 2. 共享内存（Shared Memory / SRAM）：片上每 SM 拥有 100~228 KB，带宽达数十 TB/s； 3. 寄存器文件（Register File / RF）：每 SM 拥有高达 64K 个 32-bit 寄存器，带宽超过 30 TB/s，单周期零延迟直连执行单元； - 分层分块（Hierarchical Tiling）：CUTLASS 将巨大的 GEMM 问题映射到硬件层级：CTA Tile（Threadblock 级）\(\to\) Warp Tile（Warp 级）\(\to\) Instruction Tile / MMA Atom（Tensor Core 硬件指令级），通过多级缓存复用将算术强度放大数十倍。

2. 它如何工作（结合图 1-1 与图 1-2）

CUTLASS 将 GEMM \(C = A \cdot B\)（尺寸为 \(M \times N \times K\)）严格分解为三级分块流水线： 1. CTA 级分块（Threadblock Tile）： - 将输出矩阵 \(C\) 划分为 \(M_{\text{tile}} \times N_{\text{tile}}\) 的大块，由一个 Threadblock（CTA）负责； - 在收缩维度 \(K\) 上以步长 \(K_{\text{tile}}\) 循环步进。每轮循环中，CTA 内所有线程协同将 \(A\) 的 \(M_{\text{tile}} \times K_{\text{tile}}\) 分块与 \(B\) 的 \(K_{\text{tile}} \times N_{\text{tile}}\) 分块从全局显存搬运至共享内存（Shared Memory）； 2. Warp 级分块（Warp Tile）： - CTA 内部由多个 Warp（每个 Warp 32 线程）组成。每个 Warp 负责计算 CTA Tile 内的一个子区域 \(M_{\text{warp}} \times N_{\text{warp}}\)； - Warp 内的线程协同将属于该 Warp 的数据切片从 Shared Memory 加载到每个线程的私有寄存器（Register File）片段（Fragment）中； 3. 指令级分块（MMA Atom / Tensor Core Instruction）： - Tensor Core 并不是传统单线程独立的标量 ALU，而是 Warp 协同的硬件微架构矩阵乘加阵列（图 1-1）； - 单条 PTX 指令（如 Ampere 的 mma.sync.aligned.m16n8k16，Hopper 的 wgmma.mma_async）要求 Warp 内的 32 个线程各持有特定的寄存器切片，硬件在几个周期内一次性完成小矩阵（如 \(16 \times 8 \times 16\)）的点积累加。

3. 正确性条件与常见误区

  1. 分块几何形状的硬件兼容性：
    • 顶层的 CTA Tile 尺寸必须是 Warp Tile 的整数倍，Warp Tile 必须是底层 MMA Atom 尺寸的整数倍；
    • 选取的 MMA Atom 必须与目标 GPU 计算能力（Compute Capability）和数据类型严格匹配（例如 Ampere 引入了 BF16/TF32 的 \(16 \times 8 \times 16\)，Hopper 引入了基于异步 TMA 的 64-thread Warp-Group WGMMA）；
  2. “理论算力高”不等于“实际算子跑得快”：
    • 很多开发者在没有分析 Roofline 模型的情况下，误以为使用了 Tensor Core 就必然性能暴涨；如果数据维度过小（如小 Batch Decode 阶段的 GEMV），算子瓶颈依然锁死在 HBM 显存带宽上，Tensor Core 往往处于严重饥饿闲置状态。

4. 性能与工程取舍（Roofline 模型与拐点分析）

  1. 算术强度与 Roofline 拐点（Ridge Point）：
    • 算法的算术强度定义为：\(\text{AI} = \frac{\text{总浮点计算量 (FLOPs)}}{\text{最低显存传输字节量 (Bytes)}}\)；
    • 硬件的平衡拐点（Ridge Point）为： \[I_{\text{ridge}} = \frac{P_{\text{peak}} \text{ (TFLOPS)}}{BW_{\text{peak}} \text{ (TB/s)}}\]
    • 优化分水岭：
      • 若 \(\text{AI} < I_{\text{ridge}}\)：算子处于 带宽受限区（Memory-Bound）。优化重点是增大分块复用度、消除中间写回（算子融合 Fusion）；
      • 若 \(\text{AI} > I_{\text{ridge}}\)：算子处于 算力受限区（Compute-Bound）。优化重点是优化指令流水、隐藏 MMA 依赖停顿、提升 Tensor Core 发射饱和度。
  2. Tile 增大带来的双刃剑效应：
    • 增大 CTA Tile 尺寸（如从 \(128 \times 128\) 增大到 \(256 \times 256\)）能显著提升数据在片上的复用率；
    • 负面代价：单 Block 所需的 Shared Memory 和寄存器用量剧增，导致单 SM 上能容纳的活跃 Block 数骤降（Occupancy 崩塌）；同时，若全局矩阵总尺寸较小，过大的 Tile 会导致划分出的 Block 数量甚至小于 GPU 的 SM 总数，造成大量 SM 算力闲置（波次量化损耗 Tail Effect）。

具体演示：GEMM 理想算术强度数学解析

考虑半精度（FP16/BF16，每元素 2 字节）下尺寸为 \(M=N=K=128\) 的标准矩阵乘法 \(C = A \cdot B\)： - 总浮点操作数（FLOPs）： \[\text{FLOPs} = 2 \times M \times N \times K = 2 \times 128 \times 128 \times 128 = 4,194,304 \text{ FLOP}\] - 最少全局显存传输量（输入读入 + 输出写回）： - 读取矩阵 \(A\)：\(M \times K \times 2\text{ B} = 128 \times 128 \times 2 = 32,768\text{ 字节}\)； - 读取矩阵 \(B\)：\(K \times N \times 2\text{ B} = 128 \times 128 \times 2 = 32,768\text{ 字节}\)； - 写回矩阵 \(C\)：\(M \times N \times 2\text{ B} = 128 \times 128 \times 2 = 32,768\text{ 字节}\)； - 最少总访存量：\(\text{Bytes} = 2 \times (128^2 + 128^2 + 128^2) = 98,304\text{ 字节}\)； - 理想算术强度： \[\text{AI} = \frac{4,194,304}{98,304} = \frac{2 \times 128^3}{3 \times 128^2 \times 2} = \frac{128}{3} \approx 42.67 \text{ FLOP/Byte}\] - 结论：相比逐元素加法仅约 \(0.17 \text{ FLOP/Byte}\) 的算术强度，GEMM 具备天然极高的数据复用潜力。CUTLASS 的核心工程使命，就是通过精细的分层 Tiling 让物理硬件能够逼近这一理论复用上限。

Q1 参考答案

  1. 输入阶段（Hierarchical Ingestion & CTA Tile Staging）：
    • 全局大矩阵存储于容量大但延迟高的 HBM 中。算法将全局输出空间切分为独立的 CTA Tiles（如 \(128 \times 128\)）；
    • 在收缩维度 \(K\) 上以 \(K_{\text{tile}}\) 步长循环推进，CTA 内所有线程协同将当前的 \(A\) 矩阵切片和 \(B\) 矩阵切片批量加载进片上高速共享内存（Shared Memory），完成第一级数据复用与解耦；
  2. 状态变化阶段（Warp Slicing & MMA Atom Execution）：
    • CTA 内部的各 Warp 从 Shared Memory 加载属于各自子区域的矩阵碎片（Fragment）到线程私有寄存器（Register File）中；
    • 处于同一 Warp 内的 32 个线程协同触发底层的硬件矩阵乘指令（MMA Atom，如 mma.sync 或 WGMMA），Tensor Core 微架构阵列在单指令多周期内直接对寄存器矩阵片段进行乘加点积，中间累加状态完全常驻在专用累加寄存器中；
  3. 输出阶段（Epilogue Fusion & Global Write-back）：
    • 当 \(K\) 维全部切片累加完毕后，累加寄存器中的结果经过 Epilogue（执行偏差相加、激活函数如 SiLU/GELU 融合或量化缩放转换）直接规约格式，最后以合并访存（Coalesced Store）写回全局显存的目标张量中。

Q2 参考答案

若仅观察到 Tensor Core 利用率低下，便脱离全局硬件瓶颈盲目增大 Tile 尺寸，不仅无法解决问题，反而会导致性能剧烈恶化，原因包括以下三个确定性陷阱： 1. SM 占用率崩塌（Occupancy Collapse）： - 增大 Tile（例如从 \(128 \times 128\) 提升至 \(256 \times 256\)）会使单个 Block 所需的 Shared Memory 呈平方级暴增（超出 100 KB），且每个线程需要持有更多的累加寄存器； - 这会导致单 SM 上允许并发调度的活跃 Block 数量从 4~8 个被硬件极限压缩至仅剩 1 个。当唯一的 Block 因等待全局访存流水线而发生停顿时，Warp 调度器没有任何其他备用 Warp 可供切换调度，SM 陷入彻底的停滞空转； 2. 尾部波次损耗（Tail Wave / Quantization Overhead）： - 若矩阵总尺寸规模不大（例如在小 Batch 推理或长文本解码阶段），过大的 Tile 会导致全局被切分出的 Block 总数急剧减少（甚至少于 GPU 的 SM 物理总数，例如 H100 拥有 132 个 SM，而大 Tile 仅切出 64 个 Block）； - 这会导致大量物理 SM 核心全程处于闲置状态；或者产生“尾部波次”——最后几个 Block 独自占满整张 GPU 运行，并行度严重不足； 3. 未找准根本瓶颈（Memory-Bound 误判）： - 若算子本身的算术强度远低于硬件 Roofline 拐点（例如 Decode GEMV），其根本瓶颈在于 HBM 显存读带宽已经被彻底打满，Tensor Core 是因为“等米下锅”才利用率低。此时增大 Tile 完全无法突破显存带宽上限，甚至会因寄存器溢出（Spill）引发高延迟 Local Memory 换页，使整体延迟暴涨数倍。

Q3 参考答案

根据 Roofline 性能模型，硬件的平衡拐点（Ridge Point，又称平衡转折点）由硬件规格唯一定义： \[I_{\text{ridge}} = \frac{\text{硬件算力峰值 } P_{\text{peak}} \text{ (TFLOPS)}}{\text{显存物理带宽 } BW_{\text{peak}} \text{ (TB/s)}}\] 例如对于 NVIDIA H100 SXM5（BF16 稠密 Tensor Core 算力峰值为 \(989 \text{ TFLOPS}\)，HBM3 显存带宽为 \(3.35 \text{ TB/s}\)）： \[I_{\text{ridge}} = \frac{989}{3.35} \approx 295.2 \text{ FLOP/Byte}\]

基于 Ridge Point 的优化优先级决策因果律： 1. 计算当前算子的算法算术强度 \(\text{AI}_{\text{actual}} = \frac{2 M N K}{\text{Bytes Moved}}\)； 2. 第一场景：\(\text{AI}_{\text{actual}} \ll I_{\text{ridge}}\)（极度带宽受限，如 LLM 生成阶段 GEMV）： - 最高优先级：削减全局访存量与算子融合。此时任何微调 Tensor Core MMA 流水线、展开循环的操作收益几乎为零；必须优先考虑算子融合（将 GEMM 与 Bias/SiLU/RMSNorm 融为一个 Kernel）、权重 INT4/FP8 量化（将读取字节数削减 2~4 倍）或多 Query 批处理（增大 \(M\) 或 \(N\) 以提高算术强度）； 3. 第二场景：\(\text{AI}_{\text{actual}} \gg I_{\text{ridge}}\)（深度算力受限，如 Prefill 阶段大尺寸 GEMM）： - 最高优先级：释放 Tensor Core 硬件发射流水线。显存带宽已非主要制约因素；优化重心必须转移至最大化 MMA 指令发射密度、消除 Shared Memory Bank 冲突、通过多级软件流水（Software Pipelining / Asynchronous Copy / TMA）隐藏全局内存与片上内存的传输延迟，确保 Tensor Core 持续满载运行。

### 1. 它是什么，解决什么问题

**CUTLASS（CUDA Templates for Linear Algebra Subroutines）** 是 NVIDIA 开源的高性能 CUDA C++ 模板抽象库，其 3.x 版本引入了 **CuTe（C++ Layout Algebra）** 体系。它专为榨干 Volta、Turing、Ampere、Ada、Hopper 以及 Blackwell 各代 GPU 的 Tensor Core 极限算力而生。

**GPU 硬件的深层物理矛盾与解决之道（结合图 1-1 与图 1-2）**：
- **算力与显存带宽的万倍鸿沟**：以 NVIDIA H100 为例，BF16 稠密矩阵算力峰值接近 $1000 \text{ TFLOPS}$，而 HBM3 显存带宽仅为 $3.35 \text{ TB/s}$。若每个乘加指令都需要从 HBM 提取操作数，硬件算力利用率将不足 1%；
- **存储金字塔与分层复用（图 1-2）**：GPU 拥有三级核心存储层次：
  1. **全局显存（Global Memory / HBM）**：容量大（80~144 GB），但延迟高（数百时钟周期）、带宽相对较窄；
  2. **共享内存（Shared Memory / SRAM）**：片上每 SM 拥有 100~228 KB，带宽达数十 TB/s；
  3. **寄存器文件（Register File / RF）**：每 SM 拥有高达 64K 个 32-bit 寄存器，带宽超过 30 TB/s，单周期零延迟直连执行单元；
- **分层分块（Hierarchical Tiling）**：CUTLASS 将巨大的 GEMM 问题映射到硬件层级：**CTA Tile（Threadblock 级）$\to$ Warp Tile（Warp 级）$\to$ Instruction Tile / MMA Atom（Tensor Core 硬件指令级）**，通过多级缓存复用将算术强度放大数十倍。

### 2. 它如何工作（结合图 1-1 与图 1-2）

CUTLASS 将 GEMM $C = A \cdot B$（尺寸为 $M \times N \times K$）严格分解为三级分块流水线：
1. **CTA 级分块（Threadblock Tile）**：
   - 将输出矩阵 $C$ 划分为 $M_{\text{tile}} \times N_{\text{tile}}$ 的大块，由一个 Threadblock（CTA）负责；
   - 在收缩维度 $K$ 上以步长 $K_{\text{tile}}$ 循环步进。每轮循环中，CTA 内所有线程协同将 $A$ 的 $M_{\text{tile}} \times K_{\text{tile}}$ 分块与 $B$ 的 $K_{\text{tile}} \times N_{\text{tile}}$ 分块从全局显存搬运至共享内存（Shared Memory）；
2. **Warp 级分块（Warp Tile）**：
   - CTA 内部由多个 Warp（每个 Warp 32 线程）组成。每个 Warp 负责计算 CTA Tile 内的一个子区域 $M_{\text{warp}} \times N_{\text{warp}}$；
   - Warp 内的线程协同将属于该 Warp 的数据切片从 Shared Memory 加载到每个线程的私有寄存器（Register File）片段（Fragment）中；
3. **指令级分块（MMA Atom / Tensor Core Instruction）**：
   - Tensor Core 并不是传统单线程独立的标量 ALU，而是 **Warp 协同的硬件微架构矩阵乘加阵列**（图 1-1）；
   - 单条 PTX 指令（如 Ampere 的 `mma.sync.aligned.m16n8k16`，Hopper 的 `wgmma.mma_async`）要求 Warp 内的 32 个线程各持有特定的寄存器切片，硬件在几个周期内一次性完成小矩阵（如 $16 \times 8 \times 16$）的点积累加。

### 3. 正确性条件与常见误区

1. **分块几何形状的硬件兼容性**：
   - 顶层的 CTA Tile 尺寸必须是 Warp Tile 的整数倍，Warp Tile 必须是底层 MMA Atom 尺寸的整数倍；
   - 选取的 MMA Atom 必须与目标 GPU 计算能力（Compute Capability）和数据类型严格匹配（例如 Ampere 引入了 BF16/TF32 的 $16 \times 8 \times 16$，Hopper 引入了基于异步 TMA 的 64-thread Warp-Group WGMMA）；
2. **“理论算力高”不等于“实际算子跑得快”**：
   - 很多开发者在没有分析 Roofline 模型的情况下，误以为使用了 Tensor Core 就必然性能暴涨；如果数据维度过小（如小 Batch Decode 阶段的 GEMV），算子瓶颈依然锁死在 HBM 显存带宽上，Tensor Core 往往处于严重饥饿闲置状态。

### 4. 性能与工程取舍（Roofline 模型与拐点分析）

1. **算术强度与 Roofline 拐点（Ridge Point）**：
   - 算法的算术强度定义为：$\text{AI} = \frac{\text{总浮点计算量 (FLOPs)}}{\text{最低显存传输字节量 (Bytes)}}$；
   - 硬件的平衡拐点（Ridge Point）为：
     $$I_{\text{ridge}} = \frac{P_{\text{peak}} \text{ (TFLOPS)}}{BW_{\text{peak}} \text{ (TB/s)}}$$
   - **优化分水岭**：
     - 若 $\text{AI} < I_{\text{ridge}}$：算子处于 **带宽受限区（Memory-Bound）**。优化重点是增大分块复用度、消除中间写回（算子融合 Fusion）；
     - 若 $\text{AI} > I_{\text{ridge}}$：算子处于 **算力受限区（Compute-Bound）**。优化重点是优化指令流水、隐藏 MMA 依赖停顿、提升 Tensor Core 发射饱和度。
2. **Tile 增大带来的双刃剑效应**：
   - 增大 CTA Tile 尺寸（如从 $128 \times 128$ 增大到 $256 \times 256$）能显著提升数据在片上的复用率；
   - **负面代价**：单 Block 所需的 Shared Memory 和寄存器用量剧增，导致单 SM 上能容纳的活跃 Block 数骤降（Occupancy 崩塌）；同时，若全局矩阵总尺寸较小，过大的 Tile 会导致划分出的 Block 数量甚至小于 GPU 的 SM 总数，造成大量 SM 算力闲置（波次量化损耗 Tail Effect）。

## 具体演示：GEMM 理想算术强度数学解析

考虑半精度（FP16/BF16，每元素 2 字节）下尺寸为 $M=N=K=128$ 的标准矩阵乘法 $C = A \cdot B$：
- **总浮点操作数（FLOPs）**：
  $$\text{FLOPs} = 2 \times M \times N \times K = 2 \times 128 \times 128 \times 128 = 4,194,304 \text{ FLOP}$$
- **最少全局显存传输量（输入读入 + 输出写回）**：
  - 读取矩阵 $A$：$M \times K \times 2\text{ B} = 128 \times 128 \times 2 = 32,768\text{ 字节}$；
  - 读取矩阵 $B$：$K \times N \times 2\text{ B} = 128 \times 128 \times 2 = 32,768\text{ 字节}$；
  - 写回矩阵 $C$：$M \times N \times 2\text{ B} = 128 \times 128 \times 2 = 32,768\text{ 字节}$；
  - 最少总访存量：$\text{Bytes} = 2 \times (128^2 + 128^2 + 128^2) = 98,304\text{ 字节}$；
- **理想算术强度**：
  $$\text{AI} = \frac{4,194,304}{98,304} = \frac{2 \times 128^3}{3 \times 128^2 \times 2} = \frac{128}{3} \approx 42.67 \text{ FLOP/Byte}$$
- **结论**：相比逐元素加法仅约 $0.17 \text{ FLOP/Byte}$ 的算术强度，GEMM 具备天然极高的数据复用潜力。CUTLASS 的核心工程使命，就是通过精细的分层 Tiling 让物理硬件能够逼近这一理论复用上限。

### Q1 参考答案

1. **输入阶段（Hierarchical Ingestion & CTA Tile Staging）**：
   - 全局大矩阵存储于容量大但延迟高的 HBM 中。算法将全局输出空间切分为独立的 CTA Tiles（如 $128 \times 128$）；
   - 在收缩维度 $K$ 上以 $K_{\text{tile}}$ 步长循环推进，CTA 内所有线程协同将当前的 $A$ 矩阵切片和 $B$ 矩阵切片批量加载进片上高速共享内存（Shared Memory），完成第一级数据复用与解耦；
2. **状态变化阶段（Warp Slicing & MMA Atom Execution）**：
   - CTA 内部的各 Warp 从 Shared Memory 加载属于各自子区域的矩阵碎片（Fragment）到线程私有寄存器（Register File）中；
   - 处于同一 Warp 内的 32 个线程协同触发底层的硬件矩阵乘指令（MMA Atom，如 `mma.sync` 或 WGMMA），Tensor Core 微架构阵列在单指令多周期内直接对寄存器矩阵片段进行乘加点积，中间累加状态完全常驻在专用累加寄存器中；
3. **输出阶段（Epilogue Fusion & Global Write-back）**：
   - 当 $K$ 维全部切片累加完毕后，累加寄存器中的结果经过 Epilogue（执行偏差相加、激活函数如 SiLU/GELU 融合或量化缩放转换）直接规约格式，最后以合并访存（Coalesced Store）写回全局显存的目标张量中。

### Q2 参考答案

若仅观察到 Tensor Core 利用率低下，便脱离全局硬件瓶颈盲目增大 Tile 尺寸，不仅无法解决问题，反而会导致性能剧烈恶化，原因包括以下三个确定性陷阱：
1. **SM 占用率崩塌（Occupancy Collapse）**：
   - 增大 Tile（例如从 $128 \times 128$ 提升至 $256 \times 256$）会使单个 Block 所需的 Shared Memory 呈平方级暴增（超出 100 KB），且每个线程需要持有更多的累加寄存器；
   - 这会导致单 SM 上允许并发调度的活跃 Block 数量从 4~8 个被硬件极限压缩至仅剩 1 个。当唯一的 Block 因等待全局访存流水线而发生停顿时，Warp 调度器没有任何其他备用 Warp 可供切换调度，SM 陷入彻底的停滞空转；
2. **尾部波次损耗（Tail Wave / Quantization Overhead）**：
   - 若矩阵总尺寸规模不大（例如在小 Batch 推理或长文本解码阶段），过大的 Tile 会导致全局被切分出的 Block 总数急剧减少（甚至少于 GPU 的 SM 物理总数，例如 H100 拥有 132 个 SM，而大 Tile 仅切出 64 个 Block）；
   - 这会导致大量物理 SM 核心全程处于闲置状态；或者产生“尾部波次”——最后几个 Block 独自占满整张 GPU 运行，并行度严重不足；
3. **未找准根本瓶颈（Memory-Bound 误判）**：
   - 若算子本身的算术强度远低于硬件 Roofline 拐点（例如 Decode GEMV），其根本瓶颈在于 HBM 显存读带宽已经被彻底打满，Tensor Core 是因为“等米下锅”才利用率低。此时增大 Tile 完全无法突破显存带宽上限，甚至会因寄存器溢出（Spill）引发高延迟 Local Memory 换页，使整体延迟暴涨数倍。

### Q3 参考答案

根据 Roofline 性能模型，硬件的平衡拐点（Ridge Point，又称平衡转折点）由硬件规格唯一定义：
$$I_{\text{ridge}} = \frac{\text{硬件算力峰值 } P_{\text{peak}} \text{ (TFLOPS)}}{\text{显存物理带宽 } BW_{\text{peak}} \text{ (TB/s)}}$$
例如对于 NVIDIA H100 SXM5（BF16 稠密 Tensor Core 算力峰值为 $989 \text{ TFLOPS}$，HBM3 显存带宽为 $3.35 \text{ TB/s}$）：
$$I_{\text{ridge}} = \frac{989}{3.35} \approx 295.2 \text{ FLOP/Byte}$$

**基于 Ridge Point 的优化优先级决策因果律**：
1. **计算当前算子的算法算术强度 $\text{AI}_{\text{actual}} = \frac{2 M N K}{\text{Bytes Moved}}$**；
2. **第一场景：$\text{AI}_{\text{actual}} \ll I_{\text{ridge}}$（极度带宽受限，如 LLM 生成阶段 GEMV）**：
   - **最高优先级**：**削减全局访存量与算子融合**。此时任何微调 Tensor Core MMA 流水线、展开循环的操作收益几乎为零；必须优先考虑算子融合（将 GEMM 与 Bias/SiLU/RMSNorm 融为一个 Kernel）、权重 INT4/FP8 量化（将读取字节数削减 2~4 倍）或多 Query 批处理（增大 $M$ 或 $N$ 以提高算术强度）；
3. **第二场景：$\text{AI}_{\text{actual}} \gg I_{\text{ridge}}$（深度算力受限，如 Prefill 阶段大尺寸 GEMM）**：
   - **最高优先级**：**释放 Tensor Core 硬件发射流水线**。显存带宽已非主要制约因素；优化重心必须转移至最大化 MMA 指令发射密度、消除 Shared Memory Bank 冲突、通过多级软件流水（Software Pipelining / Asynchronous Copy / TMA）隐藏全局内存与片上内存的传输延迟，确保 Tensor Core 持续满载运行。
