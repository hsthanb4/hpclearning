核心心智模型

1. 动态形状的物理困境：重编译风暴 vs 算力浪费

在传统深度学习编译器（如早期 TensorRT、XLA）的假设中，张量的维度（Batch Size BB、序列长度 SS、特征维度 CC）在启动时都是固定常数。编译器可以据此进行激进的循环展开、静态显存分配与硬件寄存器微架构特化。

然而在现代多模态大模型、自动驾驶与具身机器人中： - 语言模型的输入 Prompt 长度随时变化； - 视觉分词器（Vision Tokenizer）处理不同分辨率图像输出的 Patch 数量动态变化； - 激光雷达点云每帧检测出的有效目标物体数量完全不可预知。

图 11-1：动态形状编译的两难困境与工业级破局方案

2. TorchDynamo 的符号化推演与 Guard 爆炸

当开启 torch.compile(model, dynamic=True) 时： 1. 符号化抽象（SymInt）： Dynamo 不再将张量维度视为固定整数，而是引入一个符号变量 s0s_0。所有的中间算子计算尺寸均表示为 s0s_0 的代数表达式（如 2s0+12 s_0 + 1 或 s0//2s_0 // 2）； 2. 守卫条件（Guard）生成： 为了保证编译出的图在数学上合法，Dynamo 会生成一系列 Guard（如 s0 >= 1, s0 % 8 == 0）。在每次前向调用时，CPU 必须先以极快的速度求值这些 Guard： - 若全部命中，直接复用已编译的高效二进制内核； - 若 Guard 失败，才触发新的特化图编译。 3. Guard 爆炸危机（Guard Explosion）： 如果代码中包含大量 Python 原生整数判断（如 if x.shape[0] > 10:），Dynamo 会为每个控制分支生成独立的特化 Guard。成千上万个 Guard 会导致 Python 解释器在每次前向执行前花费数十毫秒进行条件校验，使得编译带来的加速被 Guard 检查开销完全抵消！

class DynamicShapeBucketManager:
    def __init__(self, buckets=[64, 128, 256, 512, 1024]):
        self.buckets = sorted(buckets)
        self.compiled_cache = {}
        self.recompile_count = 0
        self.hit_count = 0

    def get_bucket(self, actual_length):
        for b in self.buckets:
            if actual_length <= b:
                return b
        return None

    def dispatch(self, actual_shape):
        batch, seq_len, hidden = actual_shape
        bucket_seq = self.get_bucket(seq_len)
        if bucket_seq is None:
            raise ValueError(f"序列长度 {seq_len} 超出最大分桶 {self.buckets[-1]}")
            
        dispatched_shape = (batch, bucket_seq, hidden)
        cache_key = f"b{batch}_s{bucket_seq}_h{hidden}"
        
        if cache_key in self.compiled_cache:
            self.hit_count += 1
            is_recompiled = False
        else:
            self.recompile_count += 1
            is_recompiled = True
            # 模拟生成编译图并存入缓存
            self.compiled_cache[cache_key] = {"kernel_obj": f"compiled_engine_{cache_key}"}
            
        return {
            "dispatched_shape": dispatched_shape,
            "is_recompiled": is_recompiled,
            "cache_key": cache_key
        }

Q1 参考答案

  1. 默认策略与激进特化（Over-Specialization）： 若未显式标记动态，Dynamo 会在遇到第一个具体形状（如 Batch=3, Seq=128）时，默认将其当成不变常数进行严格特化编译，并生成一条严苛的 Guard：assert tensor.shape[0] == 3 and tensor.shape[1] == 128。 当下一次输入变为 Batch=4 或 Seq=130 时，Guard 校验失败，Dynamo 被迫再次启动耗时漫长的编译器重新生成一份全新的特化代码。循环往复，导致严重的重编译风暴。
  2. mark_dynamic 建立通用符号图： 显式标记后，Dynamo 强制将该维度实例化为一个抽象符号 s0s_0。生成的编译中间表示（IR）将基于符号代数推导，后续输入只要满足最基本的代数契约（如 s0≥1s_0 \ge 1），便直接复用同一套泛化编译内核，彻底消除 Guard 爆炸。

Q2 参考答案

  1. 传统 Padding 的算力与显存黑洞： 在 Batch 中如果有一个样本长 2048，其余样本长 128，传统做法必须将所有样本全部 Padding 到 2048。在 Self-Attention 计算时，复杂度随序列长度呈平方增长（L2L^2），导致绝大部分矩阵乘算力和显存带宽都在无情计算无效的填充零和掩码。
  2. cu_seqlens 紧凑展开机制： FlashAttention varlen 接口允许将整个 Batch 内所有有效 Token 连续平铺在一段一维显存中（总长度为 ∑Li\sum L_i），并传入一个前缀和数组 cu_seqlens = [0, L_1, L_1+L_2, ...]。 GPU 在计算每个 Block 时，根据 cu_seqlens 动态定位对应样本的起止偏移，彻底消灭所有无意义的 Padding，在多模态变长场景下将端到端吞吐提升 2~5 倍。

Q3 参考答案

  1. Optimization Profile 的硬件调优依据： TensorRT 在构建引擎时，并不是简单翻译算子，而是在目标 GPU 上对各种不同的 Tiling 切分、Warp 配置和算法实现进行实测基准压测（Benchmarking），挑选最快的内核。
  2. kOPT（最优预期形状）的物理锚定： kOPT 是 TensorRT 决定硬件微架构选型（如选择多大的 Shared Memory 瓦片尺寸、分配多少寄存器）的最关键依据。如果将范围设得过宽（如 1 到 4096），而将 kOPT 设在 2048，则当实际运行时大量请求是短序列（如 128）时，被选中的大分块内核会导致极差的 SM 活跃度（Occupancy）与极低的效率。合理配置应紧密贴合生产环境 P90 的真实流量分布。

### 2. TorchDynamo 的符号化推演与 Guard 爆炸

当开启 `torch.compile(model, dynamic=True)` 时：
1. **符号化抽象（`SymInt`）**：
   Dynamo 不再将张量维度视为固定整数，而是引入一个符号变量 $s_0$。所有的中间算子计算尺寸均表示为 $s_0$ 的代数表达式（如 $2 s_0 + 1$ 或 $s_0 // 2$）；
2. **守卫条件（Guard）生成**：
   为了保证编译出的图在数学上合法，Dynamo 会生成一系列 Guard（如 `s0 >= 1`, `s0 % 8 == 0`）。在每次前向调用时，CPU 必须先以极快的速度求值这些 Guard：
   - 若全部命中，直接复用已编译的高效二进制内核；
   - 若 Guard 失败，才触发新的特化图编译。
3. **Guard 爆炸危机（Guard Explosion）**：
   如果代码中包含大量 Python 原生整数判断（如 `if x.shape[0] > 10:`），Dynamo 会为每个控制分支生成独立的特化 Guard。成千上万个 Guard 会导致 Python 解释器在每次前向执行前花费数十毫秒进行条件校验，使得编译带来的加速被 Guard 检查开销完全抵消！

```python
class DynamicShapeBucketManager:
    def __init__(self, buckets=[64, 128, 256, 512, 1024]):
        self.buckets = sorted(buckets)
        self.compiled_cache = {}
        self.recompile_count = 0
        self.hit_count = 0

    def get_bucket(self, actual_length):
        for b in self.buckets:
            if actual_length <= b:
                return b
        return None

    def dispatch(self, actual_shape):
        batch, seq_len, hidden = actual_shape
        bucket_seq = self.get_bucket(seq_len)
        if bucket_seq is None:
            raise ValueError(f"序列长度 {seq_len} 超出最大分桶 {self.buckets[-1]}")
            
        dispatched_shape = (batch, bucket_seq, hidden)
        cache_key = f"b{batch}_s{bucket_seq}_h{hidden}"
        
        if cache_key in self.compiled_cache:
            self.hit_count += 1
            is_recompiled = False
        else:
            self.recompile_count += 1
            is_recompiled = True
            # 模拟生成编译图并存入缓存
            self.compiled_cache[cache_key] = {"kernel_obj": f"compiled_engine_{cache_key}"}
            
        return {
            "dispatched_shape": dispatched_shape,
            "is_recompiled": is_recompiled,
            "cache_key": cache_key
        }
```

### Q1 参考答案

1. **默认策略与激进特化（Over-Specialization）**：
   若未显式标记动态，Dynamo 会在遇到第一个具体形状（如 Batch=3, Seq=128）时，默认将其当成不变常数进行严格特化编译，并生成一条严苛的 Guard：`assert tensor.shape[0] == 3 and tensor.shape[1] == 128`。
   当下一次输入变为 Batch=4 或 Seq=130 时，Guard 校验失败，Dynamo 被迫再次启动耗时漫长的编译器重新生成一份全新的特化代码。循环往复，导致严重的重编译风暴。
2. **`mark_dynamic` 建立通用符号图**：
   显式标记后，Dynamo 强制将该维度实例化为一个抽象符号 $s_0$。生成的编译中间表示（IR）将基于符号代数推导，后续输入只要满足最基本的代数契约（如 $s_0 \ge 1$），便直接复用同一套泛化编译内核，彻底消除 Guard 爆炸。

### Q2 参考答案

1. **传统 Padding 的算力与显存黑洞**：
   在 Batch 中如果有一个样本长 2048，其余样本长 128，传统做法必须将所有样本全部 Padding 到 2048。在 Self-Attention 计算时，复杂度随序列长度呈平方增长（$L^2$），导致绝大部分矩阵乘算力和显存带宽都在无情计算无效的填充零和掩码。
2. **`cu_seqlens` 紧凑展开机制**：
   FlashAttention varlen 接口允许将整个 Batch 内所有有效 Token 连续平铺在一段一维显存中（总长度为 $\sum L_i$），并传入一个前缀和数组 `cu_seqlens = [0, L_1, L_1+L_2, ...]`。
   GPU 在计算每个 Block 时，根据 `cu_seqlens` 动态定位对应样本的起止偏移，彻底消灭所有无意义的 Padding，在多模态变长场景下将端到端吞吐提升 2~5 倍。

### Q3 参考答案

1. **Optimization Profile 的硬件调优依据**：
   TensorRT 在构建引擎时，并不是简单翻译算子，而是在目标 GPU 上对各种不同的 Tiling 切分、Warp 配置和算法实现进行实测基准压测（Benchmarking），挑选最快的内核。
2. **`kOPT`（最优预期形状）的物理锚定**：
   `kOPT` 是 TensorRT 决定硬件微架构选型（如选择多大的 Shared Memory 瓦片尺寸、分配多少寄存器）的最关键依据。如果将范围设得过宽（如 1 到 4096），而将 `kOPT` 设在 2048，则当实际运行时大量请求是短序列（如 128）时，被选中的大分块内核会导致极差的 SM 活跃度（Occupancy）与极低的效率。合理配置应紧密贴合生产环境 P90 的真实流量分布。
